## Problem Statement

NightOwl today enforces a sleep curfew on **one device**, with **one friend** holding the unlock key — an intentionally asymmetric 1:1 lock (`Pairing` = one `userPubkeyHex` ↔ one `friendChatId`). It cannot (a) cover all of one person's devices, so a second screen defeats the curfew, or (b) let a group of friends hold each other mutually accountable. The user wants to extend it into a collaborative, opt-in community: friends **witness** each other's curfews and hold a shared **k-of-n "multisig" key** to each other's locks, across **all of a person's devices**.

## Demand Evidence

- **Strongest evidence:** founder-as-user, n=1 circle — *"I need it for my circle."* Conviction, not market evidence.
- **Acute user:** the founder's boyfriend — sleep off the rails, hitting health, work, and the relationship. The relationship itself is the collateral.
- **Honest gap:** status quo is *"nothing structured"* — the circle talks about sleep but has built no spreadsheet, ritual, or bet. The pain is discussed, not yet acted on (yellow flag). The wedge must manufacture stakes the status quo lacks. NightOwl's hard enforcement is the asset that makes accountability real instead of swipeable.

## Status Quo

"Nothing structured." Group-chat talk, individual willpower, no shared visibility or consequence. Competing categories:
- **Soft-stakes social** (streak/habit/study-buddy apps): guilt + notifications, high churn — the "nothing structured" graveyard.
- **Hard-stakes solo** (Brick, Opal, Beeminder/StickK): real teeth, but no witnesses, no circle.
- **Open corner:** hard enforcement + mutual social witnessing. NightOwl already owns the enforcement engine and the Ed25519 friend-as-keyholder primitive — a moat streak apps can't cross and blockers never tried.

## Target User & Narrowest Wedge

- **Target:** the founder's boyfriend (acute), then the founder's couple, then opt-in circles.
- **Wedge:** the couple's mutual sleep-lock with witnessing — which in the chosen architecture is exactly the **k=1 / n=1** case of the general threshold model. Validate the dyad before opening circles to a third person.

## Constraints

- Preserve **all** v2 anti-bypass invariants: friend-held release authority, **non-cancellable 72h emergency cooldown** as the ultimate escape, per-kind scoped approvals, **no member-swap mid-lock**.
- **"Multisig" = threshold APPROVALS** (counted signed `/approve` messages), not cryptographic secret-sharing.
- Witnessing is **opt-in + minimal by default** (kept/broke curfew, streak, armed status). No raw activity, app usage, or location.
- Wire format is shared across macOS / Windows / Android; any change touches all three clients (TS + Kotlin mirror).
- Symmetric mutual-lock must **NOT** add a "my partner can let me off" button — release stays gated by threshold approval + the 72h cooldown only. This is the single most important guard against rebuilding a toothless habit app.

## Premises (agreed)

1. One primitive — **k-of-n threshold approval** — covers solo, dyad, and circle; group size is a setting, not a separate product.
2. "Multisig" means **threshold approvals**, not crypto secret-sharing.
3. Two axes kept distinct: (A) one person's multiple devices, (B) multi-person circles. Both wanted; **A's multi-device folded into the v1 along with the dyad social loop** (the "combine" decision).
4. Witnessing is opt-in + minimal by default.
5. v2 anti-bypass invariants **generalize**, they don't vanish.
6. Fun + shareable is a goal; still prove the loop with the founder's own circle first.

## Approaches Considered

### Approach A: Stitch existing primitives (minimal viable)
Two existing 1:1 pairings pointed at each other (symmetric), a thin `accountId` for multi-device, one new signed `curfew_report` relayed by the bot. Effort M / Risk Low. Ships on the proven Android+bot stack without touching the load-bearing 1:1 core. Cons: client-self-reported compliance; stitching awkward past n=2.

### Approach B: Clean Accounts + threshold model (ideal architecture) — CHOSEN
Introduce **Account** (one person = N device pubkeys + one schedule) and **Membership/Circle** (people as each other's keyholders + witnesses) with release authority modeled as a **k-of-n threshold from day one** (dyad = {1,1}). Witnessing is a first-class fan-out feed. Effort L / Risk Med. Multi-device, circles, witnessing all fall out of one model. Cons: migrates the 1:1 `Pairing` three platforms depend on; risk of building the general primitive before the dyad is proven.

### Approach C: "Sleep Room," social-first (creative/lateral)
Lead with a near-zero-setup shared room (start as a Telegram group the bot posts into): auto-posted curfew status, streaks, reactions, "who's still up?"; hard lock opt-in per person. Effort S–M / Risk Med. Fastest to the social "whoa," cold-start-friendly. Cons: risk of drifting toward a toothless streak app; could dilute the hard-enforcement identity.

## Recommended Approach

**Approach B — clean Accounts + k-of-n threshold — as chosen by the user,** with these mandatory risk mitigations baked in:

1. **Account abstraction.** One person = N device pubkeys + one schedule + one lock state. Schedule and lock state keyed by `accountId`; every device polls and enforces. Closes the second-screen enforcement hole.
2. **Membership / Circle.** People linked as each other's keyholders + witnesses. Release authority = a threshold policy `{k, n}`. **Dyad = {1,1}** — the same code path the founder validates first.
3. **Witnessing feed.** Signed compliance events (`curfew_report`) fanned out only to members who opted into that person's signals. Minimal payload: kept/broke + unlock time + streak. Telegram-native surface first (reuse the bot + existing chat), in-app feed later.
4. **Additive, backward-compatible migration.** Keep the existing 1:1 `Pairing` working. Introduce `Account` / `Membership` as new KV entities; an existing single-friend pairing maps to a `{1,1}` membership. macOS / Windows / Android current builds keep working until each is updated. **No big-bang migration.**
5. **Validate the dyad first.** Ship to founder + boyfriend as `{1,1}` across all their devices. Expose circle creation (n>2) only after the dyad sticks ~2 weeks.
6. **Release model.** Threshold approvals generalize the single-friend approve for circles; the **72h non-cancellable cooldown stays the universal escape**. **No partner-unlock button.**
7. **New wire `MessageKind`s:** `curfew_report` (compliance fan-out) and a threshold-aware release decision carrying `memberId` so the client counts approvals toward `k`. Both added to TS + the Kotlin mirror together.

## Resolved Decisions (post-review v1 spec)

These nail the mechanics an adversarial review flagged as unspecified or self-contradictory.

**R1 — Circle approvals are DEVICE-SIGNED and client-counted; the bot only relays.** This is the central fork. Unlike a v2 Telegram-only friend (who held no key), every circle member runs NightOwl and already has an Ed25519 device key (`Identity.kt` / `packages/shared` identity). A release approval is a message **signed by the approving member's device key**. Each locked client independently verifies **n distinct member signatures**, dedupes by `memberId`, and releases only when `count(distinct approve) >= k`. The bot stores/relays signed approvals but cannot forge a threshold — this preserves the v2 "a compromised Worker cannot forge" invariant. A Telegram `/approve` may act as a convenience trigger that prompts the member's device to sign, but the bot's word alone never counts toward `k`. The **member roster** (`devicePubkeyHex → memberId`) is fixed at lock activation — consistent with the v2 "no member-swap mid-lock" invariant — and the locked client counts approvals only from pubkeys in that frozen roster, never from a live bot lookup. Otherwise a compromised Worker could split one member into many pubkeys to inflate the tally toward `k`.

**R2 — Approval tally + expiry.** A release request is `{reqId, requesterAccountId, kind, createdAt}`; each approval is `{reqId, memberId, verdict, ts, sig}`. The locked client persists the tally (survives restart), counts distinct `approve` memberIds (resolved via the frozen roster in R1), and releases at `k`. Requests expire after `requestTtl` (proposed 72h — a **distinct timer** from the `emergencyCooldown` 72h escape; same duration, different purpose). Signature preimages follow the existing v2 pattern and ship in the TS signer + Kotlin mirror together: approval = `"v2|"+reqId+"|"+memberDevicePubkeyHex+"|"+verdict+"|"+ts`; `curfew_report` = `"v2|"+accountId+"|"+seq+"|curfew_report|"+canonicalJson(payload)`. Per the v2 forward-looking rule: an approval already counted is **not** retracted if that member later revokes or leaves; `k` is fixed at request creation, and a member who leaves before voting reduces `n` only for *future* requests.

**R3 — `accountId` provenance.** Bot-assigned at first enroll, stable for the person's lifetime; maps `{accountId → [devicePubkeyHex…]}`. A new device attaches via a device-join code minted by an already-enrolled device of the same account, and the attach is confirmed by an existing device's signature — so a stolen code alone cannot add a device.

**R4 — Device removal requires threshold approval.** Detaching a device from an account is a release-class action gated by the same `{k,n}` threshold. Otherwise a user detaches their own enforcing device to bypass. A lost/compromised device key is removed via the circle, never unilaterally.

**R5 — "Kept curfew" definition (resolves the offline-device bypass).** Enforcement is per-device; during curfew every registered device heartbeats `armed & enforced`. The account counts as **kept** only if no device reported a bypass/unlock AND **every registered device heartbeated `enforced`**. Any registered device that does not heartbeat during curfew is a **coverage gap — full stop**. A powered-off device is wire-indistinguishable from a force-stopped one over a poll relay, so silence never counts as "kept"; if you want a device to stop counting, **detach it via R4** (which needs threshold approval). This makes "a second device cannot defeat curfew" true: disabling/uninstalling/force-stopping NightOwl on the laptop shows as a coverage gap, not compliance.

**R6 — Witnessing opt-in is mutual + bidirectional.** The broadcaster opts in to *share* a signal; the witness opts in to *see* it; a signal flows only when both sides consent. Default shared set is minimal (kept / broke / coverage-gap, streak, armed-status) and nothing more.

**R7 — Old clients must tolerate unknown `MessageKind` (ignore, never error).** Additive backward-compat depends on the existing poll dispatch skipping unknown kinds. **VERIFIED 2026-05-25:** Android `PollLoop.kt` has `when (msg.kind) { … else -> { Log.w("unknown kind…; advancing") } }` (logs + advances the seq, no crash), and desktop `friendlock.ts:349` has a `switch (msg.kind) { … default: }`. So a future `curfew_report` lands in the else/default and is skipped gracefully on un-updated clients. Precondition holds; no pre-work needed. (Confirm the desktop `default` branch is a no-op, not a throw, when the migration starts.)

**R8 — Build phasing (resolves the "no circle code before validation" gate).** Phase 1 ships the `Account` model + the `{1,1}` release path **reusing today's single-verdict approve** (no multi-approval counting yet) — this is exactly what the founder + boyfriend dyad validates. Phase 2 adds the device-signed multi-approval tally (R1/R2) + circle creation (n>2), exercised only once a real third person appears. The general *model* (Account, threshold-shaped records) lands in Phase 1; the *counting machinery* lands in Phase 2 — so the dyad never runs unwritten circle code, and we never build the tally before a circle needs it.

**Notation:** a dyad is **two independent `{1,1}` policies**, one per account (each partner is the sole keyholder of the other) — not one shared policy. A 3-of-5 circle is one account's `{3,5}` policy naming five member keyholders.

## Open Questions

- **Compliance trust (partially resolved):** clients self-report kept/broke; R1's frozen signed roster stops a compromised bot from inflating the tally. Still open: whether circles eventually want device-attested compliance signals beyond social trust. Defer.
- **Multi-device "kept curfew" — resolved by R5** (any non-heartbeating registered device = coverage gap, full stop). Left here only as a pointer.
- **Whose schedule in a circle?** Each Account owns its own schedule; the circle holds the **release key**, not the schedule — preserves "user proposes, friends ratify."
- **Witnessing surface:** Telegram group vs in-app feed for v1. Lean Telegram-native to reach delight fastest.
- **Versioning / overlap with deferred v5 mobile-controller.** This is a release-label question, not an architecture one — the threshold primitive stays single (premise 1 holds) regardless of what we call the release. Multi-device overlaps the v5 "phone as another renderer" design; reconcile whether this ships as v6 "Circles" or absorbs v5 before building Phase 2. The v5 invariant carries forward unchanged: **a circle member's device gets no power the desktop renderer wouldn't have** — it must never become a Friend-Lock bypass.
- **Hostile / awkward-friend dynamics at n>2** (v2 docs already flag this). Threshold + cooldown mitigate; circle social design (who can see what, leaving a circle) still needs work.

## Success Criteria

- **Dyad loop:** founder + boyfriend run mutual-lock across all their devices for 2 weeks; both see kept/broke + streak; neither can unilaterally release the other except via the 72h cooldown.
- **Enforcement completeness:** a second device cannot defeat curfew — per R5, a registered-but-silent device shows as a coverage gap, not as compliant, so disabling NightOwl on the laptop can't pass as "kept."
- **Invariants preserved:** an automated check proves no release path bypasses threshold + cooldown, and no partner-unlock button exists.
- **Generalization proof:** adding a real 3rd person yields a `{2,3}` circle reusing the Phase 1 `Account`/`Membership` records **unchanged**. Phase 2 adds the multi-approval counting path — expected new code, not rework of the data model.
